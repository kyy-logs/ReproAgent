# DeepSeek 首次真实模型冒烟记录

日期：2026-10-05。平台：Windows，CPython 3.12.14，pytest 9.1.1。

## 接入

用户提供凭据后，实际请求 `https://api.deepseek.com/models` 成功。
该账户接口返回 `deepseek-flash`、`deepseek-v4-pro`；本次选择 `deepseek-flash`。
配置见 `examples/model.deepseek.json`，使用 `max_tokens`，每次最多 4096 输出 token。
协议参考：https://api-docs.deepseek.com/zh-cn/api/create-chat-completion/ 。

密钥没有写入模型配置、源码或本记录。当前 Windows 用户的本地凭据保存为
`.local/deepseek.key` 的 DPAPI 加密文本；`.local/` 已加入忽略列表。
`.local/run-deepseek.ps1` 运行时解密到进程环境变量，并在结束后恢复原环境变量。
该加密凭据不能直接迁移到其他 Windows 用户或设备。

## 案例与结果

这是一个手工构造的合成案例，不是历史 Bug 或第三方仓库基准：

```python
def parse(values):
    return [values[0]]
```

要求 `parse([])` 返回 `[]`，实际抛出 `IndexError`。已有测试验证 `parse([1]) == [1]`。
另准备独立修复版本，使用空输入保护；修复材料不进入 Agent 上下文。
每次任务最多 8 个动作、240 秒主期限、30 秒命令期限。
三次都使用原有产品代码、提示词及模型配置；第二轮仅添加本地诊断记录，第三轮补全案例描述。

## 已定位问题

契约分析提示词没有将 `missing_information` 限定为“阻止复现本次触发条件所必需的信息”。
实际模型把额外输入类型、内部错误原因等非必需问题也列为缺失信息。
第三轮甚至将明确不在范围内的行为仍列为缺失项。
控制器按照当前规则，只要契约存在任何缺失信息，就拒绝生成候选。

第二轮动作记录还显示：模型多次尝试直接写候选而未先修订契约；尝试读取契约中的
`input/issue.md`，但 read_file 工具只能读取冻结仓库及候选路径；后来读取已有测试并申请契约修订，
但用尽 8 步。不能由此断言增加步数就能解决问题。

## 建议的后续修正

1. 保持现有契约数据结构与来源验证，将分析提示词中的缺失项限定为当前报告范围的复现阻塞项。
   错误原因未知、非报告范围的行为未知不能阻止明确的输入/预期输出测试。
2. 在探索提示词中给出路径及工具参数示例，明确契约来源路径与可读仓库相对路径的区别。
3. 保留真正缺少预期行为时的阻塞规则，避免为了“通过”而直接清空缺失信息。
4. 先补充契约/上下文约束回归测试，再用同一简要描述复测；候选通过后再检查重复运行、
   修复版本和独立导出重放。

本次确认了真实供应商通信和一个提示词/控制流程问题，没有证明真实模型复现能力，
也不提供历史 Bug 复现率。后续修正尚未实施。
