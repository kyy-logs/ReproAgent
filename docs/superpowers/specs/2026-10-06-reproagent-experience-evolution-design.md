# ReproAgent 踩坑经验最小版设计

初稿：2026-10-06；架构与时序修订：2026-10-08。状态：最小版设计，用户已授权实施；经验功能尚未实现，本文不作为效果验证结论。

本修订适配当前唯一的 AgentScope 2.0.9 基础设施。探索继续使用原生 SDK ReAct；不增加定位/取证/生成的探索阶段约束。加载与写入由系统生命周期代码安排，不交给模型决定何时保存。

## 1. 第一版只验证一件事

过去记录的踩坑经验，能否让 Agent 在类似场景中少走弯路。

先实现“自动记录少量经验卡 + 简单检索 + 按需读取详情”。任务结束后自动提炼，满足机械检查即入库，后续任务自动检索；不设置人工核对或启用步骤。它是经验层的自动积累，是否提升能力仍需对照评测。

## 2. 只保留三个动作

1. **自动记录经验：** 任务结束后，从本任务允许的记录中提炼最多一条踩坑经验；没有明确可记录的现象时返回空，不强行总结。
2. **检索摘要：** 根据当前问题、包名和错误关键词，返回最多3条相关摘要。
3. **读取详情：** Agent 需要时读取其中一条经验卡，再决定当前任务的行动。

渐进加载只做两层：摘要 → 详情。进入模型的内容不包括整个经验库。

## 3. 分类保持简单

| 分类 | 内容 |
| --- | --- |
| framework | 框架、中间件、API、环境和平台的坑 |
| model | AI 编造参数、错误断言、工具参数或 JSON 协议问题 |
| workflow | 重复探索、预算用完、写了候选却没有执行 |

用 tags 补充 flask、middleware、exception、pytest、windows 等关键词。一条经验只选一个主分类；暂不建立复杂的分类树、版本范围和阶段状态机。

重叠时按记录的主要现象选类：项目本身的行为或环境限制归framework；模型理解、生成或工具调用错误归model；探索/执行/验收的组织方式归workflow。例如“中间件把异常转成响应”归framework，“因此误写pytest.raises”归model，“反复读文件耗尽预算未发布候选”归workflow。先保持三类，用tags细化，不让模型新增类别。

## 4. 一份文件，一种经验卡

经验文件由任务配置中的可选 `experience_file` 指定，推荐使用工具目录下的 `.local/experiences.json`。相对路径按任务配置文件目录解析，不按 pytest cwd 解析。未提供路径时不加载、不注册经验工具、不提炼。`learn_experience` 默认 true，只在配置经验文件时生效；设为 false 时允许读取已有经验但不写入，供冻结库评测使用。

经验库和其 `.lock` 文件不能位于目标原仓库、任务输出目录或用户提供的修复仓库内部；在准备快照前校验解析后的路径归属。它们属于工具侧持久资产，不随目标源码冻结、不安装到 pytest 副本、不交给候选写入工具。

模型只提出经验，系统校验后写入文件；Explorer 不能直接编辑经验库。第一版串行更新，不增加后台学习队列。读取不存在的文件得到空快照，不在加载阶段创建库；首次有效经验写入时才创建文件。

每条经验保留7个字段：id、category、tags、summary、detail、source_task_id、evidence_refs。最后一个字段替代人工核对入口，用于自动检查引用来源；它不证明模型的因果解释一定正确。

示例卡如下。它只是格式示意；实际记录的来源和引用由系统检查。

```json
{
  "id": "exp_由系统计算的内容哈希",
  "category": "framework",
  "tags": ["middleware", "exception", "http"],
  "summary": "通过客户端调用时，先确认异常是否被中间件转换成响应。",
  "detail": "适用条件：通过HTTP客户端调用。现象：pytest.raises 没捕获到异常，客户端得到错误响应。建议：先阅读当前项目处理层和已有测试，确认是否发生异常转换，再按有来源的预期断言响应。直接调用内部函数时仍可能抛异常，不直接套用。",
  "source_task_id": "来源轮次/任务ID",
  "evidence_refs": [{"path": "允许的原版证据路径", "content_hash": "由系统提供的真实文件哈希", "start_line": 1, "end_line": 3}]
}
```

适用条件、观察到的事实和建议直接写在 detail 中；不再拆出多个管理模块。没有确定原因时写清不确定性，不把猜测写成全局禁令。

自动提炼只输入原始问题、原版引用、候选、受控错误代码和原版执行摘要。模型返回的evidence_ids必须来自本次提供的材料；系统映射成evidence_refs并检查字段、分类、字节上限、引用归属、文件哈希和行范围，再自动写入。id和source_task_id由系统赋值，不采用模型指定的存储路径。

按分类、tags和summary的规范化内容做精确去重；重复项跳过。第一版没有置信度评分、审批状态机或自动全局规则。提炼失败、引用非法、文件损坏或写入冲突时记录原因并跳过，原复现结果不受影响。

### 4.1 经验具体怎样写入

写入放在主复现流程完成后的独立学习步骤，严格晚于探索/主模型会话关闭、导出成功或导出失败记录、最终 TaskResult 落盘。`Controller.run` 对外返回之前同步等待这个有界步骤；CLI、Claude Code 和批量评测使用同一任务入口，不能只在 CLI 打印之后添加学习逻辑。

这里区分“主复现结果已确定”和“入口函数已返回”：前者触发学习，后者在学习完成或跳过后发生。学习不改变 TaskResult 的 status、evidence_level、export_state 和主流程 duration，也不重写已发布包。额外 learning_duration、HTTP/token/费用单独汇总，整体成本分析包含它们。

DONE、BLOCKED、NEEDS_INFORMATION、EXHAUSTED 和 FAILED 均可提供原版观察，但不是每种状态必定写入：材料缺失、证据损坏、记录不可读或没有可总结现象时跳过。CANCELLED、已经设置取消信号、禁用写入或经验库读取失败时不发学习请求。导出失败仍可学习已有且完整的原版记录，不将失败的导出产物当作来源。

提炼、校验、锁获取和写入共用独立30秒预算；它不是在每次网络重试或写文件时重新计时。学习使用同一模型配置、新建的 SDK 模型资源与独立 CallContext，不能继续使用已经耗尽的复现预算或已结束的探索 AgentState。使用独立 `learning` 请求用途记账，SDK 工厂/网关显式支持该用途，无 tools、无探索步数、无协议纠正循环。最多一次逻辑请求、最多3次HTTP尝试，最后在 finally 中关闭学习客户端。学习期间取消只终止学习，已经封存的主复现结论保留。

**第一步：程序收集提炼材料。** 从当前任务挑选原始问题、原版执行、工具错误和协议错误，每段分配一个证据ID，例如E1/E2。只发送有用行段和结构化测量摘要，提炼输入最多8192字节。无法保留完整的有用片段就跳过学习，不递归摘要整个任务目录或整份包含修复版材料的报告。

材料收集使用显式允许清单：冻结的 `input/issue.md`、契约引用的已校验原版行段、当前任务候选、`execution_role=original` 的执行/失败记录，以及受控的工具或协议错误代码。禁止递归汇总任务目录；不读取 fixed 执行、修复源码、参考补丁、参考测试、评测答案、整份 task.json/report.json 或已加载的历史经验。测量字段由程序从上述允许记录计算。

先把将发送的证据一次性写入内部 `learning/evidence.jsonl`：每个 E1/E2 对应一个含 id、kind、脱敏 text 和原始来源引用的完整 JSON 行。文件不可追加或覆盖，内容哈希和行号由程序计算；模型只收到 id/kind/text，最终卡片引用这份冻结材料。原始来源引用用于追溯，但不直接引用后续仍会追加的 events.jsonl，也不引用将被重写的 task.json。文件损坏或来源验证失败时跳过学习，不让模型修补证据。

工具/协议事件只摘取受控错误码、原事件seq和payload摘要作为冻结观察，不把可变events.jsonl的整文件哈希存为原始来源引用。学习事件及模型开销只能在证据文件冻结后追加；后续追加事件不会改变经验引用的文件哈希。证据文件是内部机器记录，不是新增的用户复盘文档，不进入已经封存的复现包。source_task_id使用来源任务ID加任务目录的限定标识，防止不同评测轮次的同名任务混淆。已知凭据在提炼输入、经验文本和事件中脱敏。

```json
{
  "task_status": "EXHAUSTED",
  "evidence": [
    {"id": "E1", "kind": "verdict", "text": "semantic evidence exceeds bounded context"},
    {"id": "E2", "kind": "measurement", "text": "target_origins_count=132; observation_bytes=35079; context_limit_bytes=32768"}
  ]
}
```

上例来自已记录的核验超限现象。实际请求同时提供分类枚举、输出schema和“只总结观察，原因不确定就注明，建议必须带适用条件”的指令。

**第二步：模型提出一条经验。** 只返回以下结构；没有值得记录的经验时返回 `{"experience": null}`。模型不输出id、source_task_id或文件路径，也没有写文件工具。

```json
{
  "experience": {
    "category": "workflow",
    "tags": ["sphinx", "verification", "context"],
    "summary": "核验上下文超限时，先检查执行观察的体积。",
    "detail": "适用条件：已得到执行结果，但语义核验报上下文超限。现象：本例132个模块来源对应的执行观察超过32KB。建议：查看各字段体积，确认是否是元数据表示问题；不要无证据地把核验失败归因为测试断言错误。来源完整性检查继续保留。",
    "evidence_ids": ["E1", "E2"]
  }
}
```

**第三步：程序检查并生成最终卡片。** 严格解析JSON，拒绝重复字段、非有限值和未知字段；category必须属于三类之一，tags为最多5个非空短标签，summary/detail为非空文本，evidence_ids为本次提供的1—3个唯一ID。完整最终卡片按UTF-8 JSON序列化后最多2048字节，超限跳过，不截掉关键条件。

逐项核对证据仍属于当前任务允许的原版材料、文件哈希和行范围有效。将evidence_ids转换成程序保存的evidence_refs；source_task_id由系统提供，使用带轮次/任务位置的限定标识。引用检查只能确认来源，不能证明模型的解释一定正确，因此卡片始终是建议。

**第四步：去重。** 规范化category、tags（去空白、去重、排序）和summary（统一空白和大小写），对它们的canonical JSON计算SHA256，id为 `exp_` 加完整哈希。相同id已存在就跳过；detail不同也不覆盖旧卡。第一版不处理同义表达去重。

**第五步：安全追加到JSON。** 文件根格式固定如下，首次写入从空items开始：

```json
{
  "schema_version": 1,
  "items": []
}
```

取得不阻塞的文件锁后，重新读取最新文件，检查schema和已有条目，再做一次去重，将新卡追加到items。库文件及序列化后新文件上限均为1MiB；损坏、未知schema、达到上限或锁冲突均跳过本次写入，不重建覆盖旧库。

序列化后复用 `store.atomic_write` 的同目录临时文件、flush/fsync和os.replace流程落盘，最后释放锁。锁使用稳定的旁路文件 `<experience_file>.lock` 上的非阻塞系统锁：Windows 锁定文件字节，POSIX 使用系统文件锁；锁句柄关闭或进程退出时释放占用。不能锁即将被 os.replace 替换的库文件，也不能将锁文件存在视为占用或在释放时删除锁文件。原子替换避免写出半份JSON，锁保护“读取—去重—追加—替换”，防止更新丢失；它不意味着支持并行学习队列。

**第六步：记录结果。** 学习事件记录 `written/empty/duplicate/invalid/timeout/busy/store_error`、经验ID与模型开销；不记录原始模型响应或鉴权信息。不修改已封存的复现包；下一任务启动时才读取新经验，本任务不使用自己刚总结的经验。

拟在 `experience.py` 内提供提炼输入构建、提炼、机械检查、追加与只读经验视图；调用由 App 注入 Controller 的经验组件组织。主结果落盘后由 Controller 的有界收尾调用学习组件；读工具只持有本任务固定视图，不持有库写入函数。具体签名由实施计划固定。这里是实现约定，尚未编写产品代码。

## 5. 如何加载

### 5.1 固定库快照：任务准备阶段

配置和路径校验完成后、首次分析请求之前，读取经验文件，检查1MiB上限、schema和卡片字段，固定本任务的内存副本并记录其内容哈希。库不存在时固定为空；读取失败时本任务关闭经验读取和学习写入，保留主复现流程。中途其他任务新增经验不会进入本任务，不重新读取共享库。

此时只读取系统侧快照，不将摘要发送给 Issue 分析模型，不用经验决定当前契约。

### 5.2 摘要匹配与注入：首次探索之前

原始 Issue 冻结、IssueContract 分析完成、探索组件已绑定源码快照后，用原始问题和任务明确配置的目标模块/包名做标签与summary关键词匹配，按匹配数排序、相同分数按id排序。只提供最多3条的 id、summary；无匹配不强行注入经验。

摘要仅作为首轮 explore 输入中的独立 `experience_summaries` 提示字段，标明“历史建议，不是当前项目证据”。同一 SDK AgentState 跨轮保留它，候选失败或契约修订后不重复注入、不重新检索。分析模型、契约修订分析、Verifier、Runner和Exporter都不接收经验文本。

### 5.3 详情读取：探索模型主动调用时

配置经验且固定视图读取成功时，在SDK Toolkit中增加只读 `read_experience(id)`；未启用或库读取失败时保留原六工具面。空库属于成功读取的空视图，但没有可读取的ID。同步更新运行时允许工具集、回复协议检查与权限中间件，不能只注册工具而被白名单拒绝。它不是结束阶段的领域工具，不产生PhaseResult。

只接受本任务已提供摘要的ID，从固定内存副本读详情；不能传文件路径、遍历共享库或返回其他任务记录。每任务最多成功读取一条详情，额度跨候选重试和契约修订共享；成功读取后再次调用明确拒绝。未知ID/读取拒绝仍消耗该次探索请求的步数，但不算成功读取。

摘要与成功读取详情的模型可见JSON内容合计最多2048字节，按实际UTF-8序列化表示计算。不足以容纳完整详情时拒绝读取，不截掉适用条件或不确定性。摘要选择可少于3条以满足容量；文件哈希、source_task_id和内部证据追溯不作为详情正文发送。详情工具请求计入同一个20步探索预算：模型发出工具调用时扣一步，工具本身不重复take_step。沿用已有发布预留规则，事实充分且只剩3步时也限制读经验；不新增探索阶段状态机。

经验ID和内容不能作为当前契约/候选验收的原版来源引用。模型需要用原始 Issue 或当前源码重新确认建议是否适用。

```text
新 Bug → 检索最多3条摘要 → 按需读取1条详情 → 生成并执行新测试
```

经验只给 Explorer 提示。当前预期仍来自原始 Issue/项目来源；新测试仍走现有核验、重复运行和可选修复版验证。Verifier 的语义判定不加载经验。

## 6. 最小实现结构

新增一个 `src/reproagent/experience.py`，负责提炼输入构建、机械检查、JSON读写、摘要匹配和按ID读取详情；不新增数据库、外部服务或一套Agent编排。

App 根据可选配置组装经验组件，并提供使用同一模型配置、独立资源生命周期的学习 gateway 工厂；Controller 安排加载、首次探索提示、封存后学习，SDK Explorer 注册只读详情工具。只有 AgentScope 一条底座路径，不恢复旧 native 后端。默认关闭，通过配置经验文件启用；空库仍可以在任务结束后学习，没有命中时复现路径照常运行。

每任务最多一次逻辑提炼请求；网络重试使用 SDK 工厂的同一套有界规则，最多3次HTTP尝试，不加协议纠正循环。提炼输出上限沿用配置的模型上限，30秒内的超时、取消和资源释放均有边界。学习请求用途明确记录为 learning，不伪装为 contract/verdict；所有尝试与token单独记账。

加载/读取/自动新增的经验ID及跳过原因写入现有任务事件。report.md只增加复现期间实际读取的经验ID；任务结束后的提炼开销和新增经验ID写入事件及CLI汇总，不改写已经封存的导出包，也不新增需要用户核对的复盘文档。

### 6.1 生命周期总顺序

```text
校验配置、路径
  → 固定经验库快照（仅程序可见）
  → 冻结源码和原始Issue、检查目标环境
  → 原始Issue分析（不带经验）
  → 首次探索注入最多3条摘要
  → ReAct按需read_experience（最多1条）
  → 发布候选、真实执行、Verifier、独立重复、可选修复验证
  → 关闭主探索会话和主模型资源
  → 导出完成或失败，最终TaskResult落盘
  → 可选学习：冻结允许证据 → 新建学习请求 → 校验去重 → 原子写库
  → 关闭学习资源、记录学习结果与额外开销
  → Controller.run返回原TaskResult，CLI输出主结果和学习汇总
```

新卡只供后续任务使用。本任务不重新加载，也不追溯改变报告。主任务的终态和学习 written/empty/duplicate/invalid/timeout/busy/store_error 是两套独立结果；未启用、只读评测或用户取消分别记录 skipped_disabled/skipped_read_only/skipped_cancelled。

## 7. 保留三条底线

- 经验是提醒，不能覆盖当前源码和执行事实，也不能自行修改工具、预算或成功判定。
- 记录只来自原始问题、原版代码与原版任务记录；隐藏修复代码、参考测试和提示不进入经验。
- 入库自动做来源与结构检查；经验仍可能包含错误解释，因此只作为可忽略的建议，每个新候选都重新执行和核验，不把经验升级为硬性规则。

## 8. 如何验证最小版

时序回归必须证明：分析/Verifier的模型请求不含经验；首轮摘要只注入一次；库在运行中更新不影响本任务；详情跨探索轮次只读取一次且工具不双扣步数；learning请求晚于主会话关闭、包发布和最终TaskResult落盘；新增经验不出现在本任务包内；用户取消、库损坏和只读模式不发学习请求；主预算耗尽后学习仍只使用自己的30秒。冻结学习证据在追加事件后哈希不变。任一学习失败不能覆盖已经保存的复现结论。

先在学习任务集自动产生少量经验卡，冻结文件后，在不重叠的新任务上对比关闭经验/开启经验。评测期间关闭写入，不能把评测失败立即学回当前库。

固定模型、预算、目标环境和经验文件。记录有效差分交付、重复读取、无效工具调用、步骤数和额外成本；检查经验有没有诱导错误断言。全部失败仍保留，不仅展示受益案例。

通过有经验和无经验的对照，确认至少存在可解释的受益案例，并检查负面影响后，再决定是否扩展。少量案例不用于宣称普遍成功率提高。

## 9. 以后再加

更强的自动经验效果验证、库版本发布与回滚、向量检索、离线策略优化和模型微调留在后续。自动提炼、机械检查和入库属于本最小版。

基础接入以当前 SDK 流水线及已完成的边界修复为前提，真实模型能力仍单独评测。本文确定经验最小版范围和时序，不把经验辅助用于掩盖核验和交付问题，也不承诺经验已提高复现率。
