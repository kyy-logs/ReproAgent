# ReproAgent 经验复用价值与写入质量设计

日期：2026-10-27（Asia/Shanghai）

状态：讨论范围已确认；本文待用户审阅，尚未进入实现计划或实现。

代码核对基线：`feat/ai-tool-integration`，`b7842c6`。实施前重新确认工作区。

相关设计：[轻量草稿与审查](2026-10-25-experience-draft-review-design.md)。

## 1. 目标与边界

用户要求的是对后续任务有帮助的经验卡。仅仅发生过错误、存在合法引用、成功写入库，均不足以证明值得复用。

本版要求卡片说明：后续什么可识别条件下适用；能改变哪个具体动作或判断；相对已有工具规则、当前 Issue 增加了什么；结论有哪些证据和限制。允许任务最终失败时产生有依据的负面经验，允许没有验证过的替代方案，但不得将建议写成已验证方法。

本版不承诺每个任务产卡，不要求所有卡都包含成功配方，不让人工逐卡审批。保持三个分类和现有目录/正文接口；不引入向量库、第三个审查模型、置信度分数、额外执行验证或卡片生命周期系统。

先修写入质量。相关性召回、目录排序、强制读正文、跨任务泛化和实际收益另行验证；本版不以这些功能的设计替代写入问题。

## 2. 已核对的问题

本地证据：`repro-results/experience-card-audit-20261027/REVIEW.md`，以及原批次、只读重跑的完整产物。这些是本地审查资料，不是随安装包分发的依赖；实现测试需构造脱敏、可独立运行的最小材料。

| 观察 | 本版回应 |
| --- | --- |
| 五张实验卡均由 legacy 路径产生，没有 experience.review | 新质量验收明确使用 draft_review；不拿 legacy 运行冒充审查验收 |
| 5227 把旧版本缺少 pytester fixture 主要归因于插件没加载 | 材料保留实际失败阶段/可用接口；审查区分观察和假设，不凭缺失异常推断唯一原因 |
| 15678 两个不同拒绝被合成“缺断言” | 保留逐候选的断言与诊断绑定，避免不同尝试间串因果 |
| 18621 大量重复 Issue 和报错 | 把复用增量作为独立审查条件，允许 NO_REUSABLE_LESSON |
| 8365 引用的代码和确认执行属于不同候选 | 主张哪种写法得到验证，就必须绑定该候选，不能仅因测试名相同借用结果 |
| 后续任务读取了不相关框架卡 | 保持目录短描述与正文范围一致；本版不声称已解决选读相关性 |

## 3. 方案选择

| 方案 | 取舍 |
| --- | --- |
| 仅修改提示词 | 成本小，但缺失断言定位、失败细节时，审查仍只能猜 |
| **补齐有界材料，收紧现有审查** | 采用；复用现有一次 review、证据胶囊、校验器和写库链 |
| 对每条经验额外运行验证 | 不采用；需要新环境和预算，也不能自动证明跨任务适用 |

不新增独立“价值评分”调用。探索者仍在原有提交动作中给草稿；程序组装材料；现有学习模型独立审查兼整理；程序负责引用、格式、预算与最终写入。

## 4. 总体流程

```text
探索者提交一个具体踩坑草稿，或显式 none
    ↓
程序关联原版工具/候选/执行/诊断，组织有界材料
    ↓
现有 review：证据支持 + 适用边界 + 可执行决策 + 复用增量
    ├─ accept：保留有价值且有依据的教训
    ├─ revise：去除猜测、收窄范围后仍有价值
    └─ reject：无依据、矛盾，或无复用增量
    ↓
程序校验既有六字段及引用 → 原有追加/索引流程
    ↓
后续任务按原有目录与正文接口读取
```

经验处理仍在主任务结果落盘后的既有时机运行；失败、不产卡、不合格输出不改主任务结果。新卡不在当前任务中即时回灌。

## 5. 材料：补关键差异，保持 8 KiB

### 5.1 必须区分的内容

诊断材料应保留候选、契约版本、实际运行与 verdict 的绑定。当前只保留诊断 code/origin，不足以区分缺断言、断言无依据、断言未执行等情况。

对于草稿所引用、可关联到具体候选的拒绝，新增可核验的诊断材料原子，至少包括：

- candidate_id、run_id、contract_id/version，以及用于核对绑定的 manifest_hash；
- classification、原始诊断 code/origin；
- 已记录的失败阶段和失败节点；
- 若诊断定位到断言：实际 assertion_id、源码位置、经过冻结候选校验的完整断言片段；
- 受限的拒绝理由，保留其来源身份及内容完整性。

程序只能复制实际存在且绑定有效的字段。不同候选/运行不合并为同一原因；找不到断言身份时明确未知，不根据错误码生成断言或根因。当前 SDK 工具错误仍保留真实参数、结果和调用关联，不将“工具错误”直接归因于目标项目。

新增诊断使用封闭字段集合，按既有规则进行已知凭据脱敏，再冻结到学习证据胶囊；诊断正文、候选代码仍是不可信数据，不能作为指令执行。脱敏不等于通用秘密扫描，不扩大采集到任意日志、异常对象或宿主文件。

Verifier 的模型理由保持 `provider_claim` 身份，不能升级为程序事实。任务 EXHAUSTED 只表示资源耗尽，不能作为某种代码写法错误的证据。

### 5.2 预算与省略

- 学习请求总 JSON 继续限制为 8192 UTF-8 字节，单个材料原子继续限制为 2048 字节。
- 先满足已有必需材料，再优先放入草稿直接相关的具体诊断、对应候选片段和实际结果；无关工具错误排后。
- 每次最多补入两条具体诊断原子，按与草稿来源的关联优先，不按报错数量堆材料。
- 大理由可以保留有明确摘录标记的片段；需要理解的断言本身放不下时，省略该原子并记录原因，不静默截断成另一条表达式。
- 必需材料装不下沿用已有超限跳过；可选材料装不下只省略该项，不清空其他可用材料。
- 缺失/被省略的原因不得由模型补齐。剩余材料不能支持具体教训时，审查拒绝或不产卡。

不读取整段探索历史、fixed 源码、参考补丁、隐藏测试或旧卡正文来补因果。本版也不新增 fixed 结果投影；材料没有提供差分验证依据时，卡不得声称方法已通过 fixed。后续若支持结果元数据，需另行设计绑定和泄漏边界。

## 6. 草稿和卡片表达

保留现有 `situation / observation / lesson / source_ids` 草稿字段，以及既有卡片的六个提议字段：category、tags、description、summary、detail、evidence_ids。不增加版本不兼容的必填字段。

在现有字段中表达：

| 字段 | 责任 |
| --- | --- |
| situation / description | 何时值得加载；包含有证据的组件、操作、症状及必要版本/平台条件 |
| observation / summary | 实际动作和结果，避免把推测混成事实 |
| lesson / detail | 应避免的具体动作、下一步判断或检查、证据边界 |
| source_ids / evidence_ids | 指向实际来源，不能靠正文写 ID 代替合法引用 |

每张卡只围绕一个决策点。可以用多个证据支持同一教训，不能把无关错误拼成一张“注意各种问题”的卡。

建议正文按“适用条件；已观察事实；下次动作；验证边界”组织自然语言。负面教训可以只有禁止的动作和边界，不要求虚构成功替代方案。模型不知道版本就写未知，不能添加经验中没有的版本号。

目录 description 必须与正文一致，不能把“某版本 fixture 不存在”扩写为“所有 pytest 测试适用”，不能把“尚未验证的检查方向”包装为通用解法。保持 description ≤160 个 Python 字符、最终卡 ≤4096 UTF-8 字节及原有严格诊断。

### 示例：有价值但未声称整个任务成功

```text
适用：旧版 pytest 中 pytester fixture 缺失，且实际可用列表/源码提供 testdir。
观察：添加插件声明仍未提供 pytester；setup 在目标断言前失败。
动作：先核对该版本真实的 fixture/API 名称，区分名称不存在与插件未加载；
      没核对前不要反复只改插件声明。
边界：证据支持这一检查顺序，不证明改用 testdir 后整个复现任务会成功。
```

这是针对本地已核对材料的设计例子，不能让模型在没有对应证据的任务中照抄。

## 7. 现有 review 的准入标准

审查必须同时检查事实支持与后续行动价值。事实正确但只复述 Issue，不应自动 accept。

准入问题：

1. 后续任务可以识别适用条件吗？范围是否有证据、是否过宽？
2. 读完后能少做哪个错误动作，或多做哪个具体检查？
3. 相对当前 Issue、已知工具规则，新增了哪条有依据的区别或边界？
4. 建议是否受到同一候选/执行事实支持？有没有将多个变化或不同拒绝混成因果？
5. 观察、推测、条件建议和已验证结果是否区分？

“工具规则重复”不按关键词机械拒绝：如果增加了非显然的版本差异、失败前置条件或操作顺序，仍可以有价值。相反，“必须补断言”这类话即使合理，也不能由两次不同原因的 INVALID_CANDIDATE 自动证明。

沿用现有响应和原因码：

- accept / SUPPORTED：以上条件满足；
- revise / SCOPE_NARROWED：删除猜测、混杂内容或收窄条件后仍有具体价值；
- reject / UNSUPPORTED、CONTRADICTED：支持不足或矛盾；
- reject / NO_REUSABLE_LESSON：没有新增的可执行教训，包括空泛提醒、纯 Issue 重述。

程序继续校验来源、响应字段和大小；模型负责语义判断。本版没有程序性证明“卡一定有用”，不将 accept 或高质量文案当效果保证，不新增第二次纠错/审查请求。

## 8. 路径兼容与旧卡处理

- 本次严格准入以显式 `experience_mode=draft_review` 为目标；复用现有审查调用，不增加第三个模型。
- 保留 legacy 配置、库格式和读取行为，不静默把 legacy 变成两个付费调用，不把默认模式切换藏在本次修复中。
- 共享材料投影如被 legacy 复用，也必须保持其来源和预算约束；不把材料增强等同于独立审查。
- 历史五张卡不自动改写、删除或升级成“已审查”。验证使用独立空库或明确冻结的测试库，防止旧卡污染质量实验。
- 目录浏览、正文读取配额和提示时机本版不变，不以强制阅读掩盖卡本身质量。

## 9. 影响范围

预期涉及 `learning_material.py`、草稿说明所在的探索提示/工具 schema 文案、`prompts/review_experience.md`、必要的学习提取说明、`docs/experience.md` 与对应材料/SDK 审查链测试。实现计划需要按当时源码确定精确文件和测试位置。

不修改 Controller/Verifier 的主任务判定、候选执行、源码引用资格、fixed 隔离、分类存储结构、目录读取 API、全局预算或经验默认模式。对来源和诊断的调整仅用于学习投影，不能反向改写原 verdict。

## 10. 验收

### 离线机制

- 两个候选的不同拒绝原因保留各自绑定，不能合并；错误哈希/候选/契约关联不得进入材料。
- provider_claim 仍是 provider_claim；缺失字段、摘录和省略保持明确。
- 8 KiB 总预算、2 KiB 原子边界、无关错误优先省略、必需材料超限均有测试。
- 无复用增量的材料可产生 NO_REUSABLE_LESSON，且不写正文或索引。
- 有独立证据的局部负面经验，即使任务 EXHAUSTED，也能合法接受；没有成功替代方案不能单独构成拒绝理由。
- 合法草稿经一次 review 写卡并读回；显式 none、坏响应、审查拒绝、写库失败仍不改变主任务。
- 既有 ID/分类/字数/引用/长路径/工具配对/权限隔离和 legacy 兼容性继续成立。

脚本化响应只能证明机制和材料交付，不能证明模型学会审查。

### 真实模型定点质量验证

另行授权后，先使用冻结材料验证三个正反场景，而不重跑完整探索：

1. 5227 型：有版本/API 的独立证据时形成具体兼容性检查，不推断“只需加载插件”；
2. 15678 型：不把断言无依据与没有断言合并，不从 code 猜唯一根因；
3. 18621 型纯 Issue 复述应允许拒绝，同时设置确有新增局部负面教训的正例，防止一律拒绝。

每份材料只按预注册调用次数执行，保留不理想输出，不以重复请求挑出合格卡。通过意味着本组质量样例符合准入标准，不证明稳定性或实际收益。

### 后续任务效果

只有定点质量通过后，才设计冻结库、模型/预算/环境一致的后续适用任务对照。避免同一案例不同初始契约造成混杂；模型选读、正文可达、行动变化与差分成功分别记录。用跨任务样本评估迁移，不能把同 Issue 重跑当泛化。

本设计不授权付费实验，不预设样本数量或宣称收益。卡片数、review accept 数、读卡次数均不作为最终成功指标。

## 11. 已知限制

语义准入仍依赖模型，可能误收或误拒。8 KiB 预算可能无法容纳必要的版本或断言上下文，此时宁可少学。只在草稿已有来源中审查，不能保证捕获整个探索过程中最有价值的教训。旧库与 legacy 仍存在历史质量问题，相关检索也尚未修复。

用户审阅本文后，再编写逐项实现计划；本阶段不改产品、不重写旧库、不运行付费模型。
