## 结论

保留 Python + pytest、用户提供可运行环境、固定控制流程加单 Agent 的架构。原稿的模块拆分可以继续使用，主要问题集中在验证与执行契约，已直接修订原文。

本次完成的是设计审查，没有实现 Runner、运行真实项目或验证复现率。导入绑定、pytest 结果采集和进程树清理仍需在实施阶段用实际项目和操作系统验证；不能把规格修订当作实现已通过测试。

## 与后续优化的边界

- 干净工作副本和证据绑定属于 MVP；多候选策略、缓存与恢复仍属于后续优化。
- MVP 最终用例已经检查正确行为；后续回归测试交付是风格整理与补丁包装，不重新引入断言正确性。
- 新增可选输入只用于明确代码来源和测试位置；用户不必重新安装环境，无法推导时报告具体阻碍。
- 没有扩大到自动修复、多语言、浏览器操作或托管服务。
- 2026-10-05 用户进一步确认：运行受阻后自动缩小执行范围、寻找替代入口，作为后续优化。MVP 保留可运行目标测试环境的前提，受阻时交付诊断；未来 `ExecutionPlan` 不属于本轮第一版验收。

## 关键外部依据

- pytest fixture 的可见性与目录、模块、类作用域相关，不能假定统一临时目录能够访问其他测试子树的 fixture。[官方 fixture 说明](https://docs.pytest.org/en/stable/reference/fixtures.html#fixture-availability)
- pytest 导入模式可能影响测试针对本地源码还是已安装包运行，因此需要检查实际测试进程中的来源。[官方导入机制说明](https://docs.pytest.org/en/stable/explanation/pythonpath.html)
- pytest.raises 用于检查预期异常；将不应出现的 Bug 异常作为预期，会反转最终测试含义。[官方异常断言说明](https://docs.pytest.org/en/stable/how-to/assert.html#assertions-about-expected-exceptions)
