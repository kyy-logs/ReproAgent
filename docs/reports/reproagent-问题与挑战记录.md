## P01：探索由模型决定，任务是否完成由谁决定

### 原先容易混在一起的两种控制权

第一种是“下一步看哪个文件、查什么符号、生成什么测试”，这需要模型根据已经看到的代码和工具反馈决定。

第二种是“这个候选是否真的执行过、是否可接受、是否需要独立重跑、任务能否结束”，这必须由程序根据实际记录决定。模型不能通过普通文本直接提交成功状态。

### 当前的职责划分

| 角色 | 实际负责的事情 | 不能仅凭它完成的事情 |
| --- | --- | --- |
| 探索 Agent | 选择读取/搜索，形成候选，提出契约修订或请求信息 | 自己宣布已经通过执行和验收 |
| Controller | 消费阶段结果，安排运行、验证、重复确认、可选修复版对照与导出 | 把一个未经核验的模型结论当成执行事实 |
| Runner | 在新副本实际运行候选，保存原始执行、探针和保护结果 | 仅根据退出码判断失败是否对应 Issue |
| 验收路径 | 根据绑定、执行与来源事实决定是否接受候选，再形成可用结论 | 用历史建议替代本次原版证据 |

实际流程可以概括为：

```text
模型探索并发布候选
  → Controller 确认候选是本任务真实发布的记录
  → Runner 在新副本运行
  → 形成验收结果
  → 未接受：反馈具体原因，继续调整或报告缺失信息
  → 已支持单次复现：独立重跑
  → 重复确认后：可选修复版对照，再导出
```

### “当前任务视图”在这里是什么

程序会向探索阶段提供当前契约、项目视图、历史/阶段记录、反馈、Issue，以及启用时的经验目录入口。这些字段由实际状态生成，不能只靠模型记住几百条聊天自行推断进度。

不过，模型仍有消息历史；不能把当前实现说成完全没有历史、只消费一份状态 JSON 的运行时。

### 一个具体例子

模型发布一个测试后，即便随后输出“我已经复现了”，Controller 仍需安排执行和核验。如果第一次观察被认可、独立重跑却没有确认相同问题，就不能提升为重复观察。反过来，模型选择先继续查源码，也不等于它拥有任意更改业务状态的权限。

这个分工让探索保持灵活，同时使“为什么接受”落到真实记录上。当前没有额外实现一套持续限制探索路径的阶段规则，不能把这种设想写成已上线能力。

依据：[Controller](../../src/reproagent/core/controller.py)、[AgentContext 和 TaskResult](../../src/reproagent/core/models.py)、[架构设计](../archive/specs/2026-10-05-reproagent-architecture-design.md)。

## P02：防止“修改源码，把测试改红”制造复现

### 需要防的并不只有直接编辑源文件

一个红色测试可能来自多种无效路径：修改了原版实现；导入了本机另一个安装版本；放入影子模块替代目标包；改写测试配置；发布后又修改候选；或者根本没有执行到目标代码。

因此，“pytest 返回非零”本身远远不够。我们需要确认失败发生在目标原版和该候选之间，而不是 Agent 人为制造的另一个场景。

### 当前保护如何逐层起作用

| 环节 | 具体做法 | 想阻断的问题 |
| --- | --- | --- |
| 冻结原版 | 对纳入快照的文件生成清单和内容哈希 | 后续偷偷更换原版内容 |
| 发布候选 | 仅允许配置测试区域内的新 test/data 文件，拒绝覆盖保护文件 | 通过候选覆盖源码或已有测试 |
| 限制配置文件 | 不允许候选引入 conftest.py、pytest.ini、依赖文件等受限文件 | 改变加载、插件或测试配置来影响结果 |
| 固定候选 | 生成 manifest，执行前核对文件与清单哈希 | 发布的是 A，运行时变成 B |
| 新副本运行 | 从冻结快照复制并安装候选，不覆盖原版/修复版已有同名文件 | 历史运行残留或安装覆盖造成干扰 |
| 运行后保护 | 检查原版文件修改、删除、非许可新增以及候选内容 | 运行测试时修改文件制造结果 |
| 来源核对 | 核验观察到的目标来源位于运行副本，并匹配原版清单 | 导入安装包、外部文件或不可信来源 |

### 一个具体例子

原版 `parse([])` 会抛 IndexError，预期应该返回空列表。合法候选可以新增：

```python
from example.parser import parse


def test_empty_input():
    assert parse([]) == []
```

如果候选提案还包含对 `example/parser.py` 的覆盖，发布阶段就应拒绝；如果测试运行期间把受保护文件改了，运行后保护也应识别。例子说明的是护栏作用，不是一个新的真实案例结果。

### 文件保护仍有哪些边界

当前检查主要是发布约束、文件完整性和来源证明，不是对任意 Python 行为的全面证明。例如，只在内存中 monkeypatch 对象，未必留下文件哈希变化；测试仍有可能构造无关断言。这也是为什么不能只靠文件保护就认定 Bug 语义正确。

同样，文件副本不能限制全部网络或系统副作用。需要将“保护覆盖了什么”和“已验证了什么”分开说明。

依据：[Workspace 发布与保护](../../src/reproagent/workspace.py)、[Runner](../../src/reproagent/runner.py)、[技术边界说明](../technical-highlights-and-output.md)。

## P03：修复版执行受阻，与完整执行后的验证失败不是一回事

### 为什么要单独记录修复版结果

原版重复出现同一问题，证明的是重复观察；相同候选在兼容修复版通过，才进一步支持差异验证。这两个结论不能被一个“成功/失败”开关混在一起。

特别是修复版运行不完整时，不能说“修复没有效果”；完整运行后保护检查失败时，又不能说“只是环境暂时跑不动”。两者需要不同处理。

### 当前分类

| 修复版情况 | fix_validation_status | 可以给出的结论 |
| --- | --- | --- |
| 没提供或尚未进入对照 | not_provided | 没有修复版对照结论 |
| 环境准备失败，或执行超时、探针不完整等 | blocked | 对照受阻，没有完成有效验证 |
| 完整运行，但相同候选仍失败或验证不兼容 | failed | 没获得修复版通过 |
| 完整运行，但实际源码保护失败 | failed | 执行记录不满足保护条件，不能接受对照 |
| 相同节点实际执行、通过，且来源/框架/保护等要求满足 | passed | 在原版重复确认基础上形成差异验证 |

取消、进程清理失败和全局终止仍有自己的控制路径，不能把这些情况也全部包装成普通 blocked。

### 当时审查抓到的具体问题

实现曾对所有执行诊断统一写 `blocked` 和“execution incomplete”。但 SOURCE_PROTECTION_FAILED 也可能来自已经完整退出、探针完整的运行。把它归为“没有跑完”会误导下一步处理。

修复后，只对执行未完成使用受阻语义；真实保护失败恢复为 failed，并保留具体诊断。对应回归会在 fixed 运行后实际修改文件，确认程序不会把它当作普通执行不完整。

### 一个容易误读的组合

假设原版已经独立运行两次并确认问题，但 fixed 执行超时，可能出现：

```text
主任务：DONE
证据等级：REPEATED_OBSERVATION
fix_validation_status：blocked
```

这不表示修复版通过了；DONE 表示当前主任务流程与交付完成，证据范围仍以等级和 fixed 状态为准。只有对照满足要求，才能提升到 DIFFERENTIAL_VALIDATED。

依据：[修复版验证实现](../../src/reproagent/core/controller.py)、[对应回归](../../tests/unit/test_controller_execution_recovery.py)、[执行恢复验收](../archive/reviews/2026-10-14-execution-diagnosis-recovery-acceptance.md)。

## P04：复用探索聊天总结，还是独立总结上下文

### 当时争论的核心

继续使用探索上下文有明显好处：模型刚经历完整过程，知道查过什么、为什么换候选，以及哪些地方反复碰壁。问题是这些消息同时混有猜测、早期假设、无关输出和已被否定的结论。直接让它总结，可能把“曾经以为如此”写成“已经证实如此”。

完全新开上下文又有另一种风险：如果只给最终结果，就只知道“最后成功/失败”，看不到中间踩过的坑。因此最终选择不是只给结论，而是**同一模型配置、独立总结上下文，程序提供有依据的代表性过程**。

### 谁负责什么

| 环节 | 负责方 | 产物 |
| --- | --- | --- |
| 保留经历中的可核查事实 | 运行过程及事实采集逻辑 | 工具调用、拒绝、源码引用、候选和原版执行记录 |
| 整理学习输入 | 程序 | 带 EID 的材料、代表性尝试及实际省略说明 |
| 提炼一条值得复用的建议 | 使用相同模型配置的独立学习客户端 | 结构化经验提案，也可以不提出经验 |
| 校验并持久化 | ExperienceService 和存储逻辑 | 有合法字段、来源引用和大小约束的经验卡 |

学习请求不提供直接编辑经验库的工具，也不是由探索 Agent 自己把一段自由文本追加到库里。模型负责提出内容，程序决定是否接受、如何生成元数据和如何落盘。

### 什么时候发生

```text
主探索结束并关闭探索资源
  → 完成或尝试导出
  → 最终 TaskResult 落盘
  → 独立整理并冻结学习事实
  → 独立学习请求
  → 程序校验提案与来源
  → 原子追加经验
  → 后续任务冻结库时才看见新卡
```

学习发生在主结果封存后，不回头修改本次判定。只读、取消、坏库或没有可信材料时有跳过路径；经验并不限定只从成功任务产生，但失败任务必须有足以支持建议的事实。

### 输入如何包含“踩坑经历”

输入可以保留冻结 Issue、校验过的原版引用、代表性候选、原版执行和验收结果，以及实际工具拒绝/操作测量。例如：第一次候选提交被拒，返回了真实错误；后续读到相应源码，再形成另一个候选。两次候选的差别及结果可以成为材料，而不是只剩一个最终状态。

原材料冻结在任务内的 `learning/evidence.jsonl`，卡片通过哈希和行号引用。模型返回 evidence_ids，由程序映射为引用；不能把模型自己写的“E1 证明了……”直接当作合法来源。

修复版执行、隐藏答案、参考修复补丁和旧经验正文不会作为本次学习事实。这使建议尽量来自本次实际遭遇，而不是答案泄漏或历史建议的自我复制。

### 一个机制示例

假设事实里确实记录了“源码引用范围没有被工具完整展示，因此修订被拒绝”，模型可以提炼：修订前应读取将要引用的完整范围，而不是只记住一句“修订失败”。

但它不能仅凭一次拒绝就总结成“某个目录永远不能读取”，也不能把后来成功归因于唯一某个动作。代表性过程不是完整历史，时间先后仍不能单独证明因果。

当前不引入人工逐卡核对，因此自动来源、字段和存储校验更重要；这些程序检查保证的是可追溯与格式边界，不保证建议语义和效果必然正确。

依据：[经验生命周期与材料](../experience.md)、[ExperienceService](../../src/reproagent/experience.py)、[学习材料整理](../../src/reproagent/learning_material.py)。

## P05：学的是工具与流程教训，检索却只看 Bug 文本

### 为什么同一个用例学出的卡也可能找不到

早期检索主要看卡片标签/摘要与 Issue、target_modules 的字面重合。但历史教训的关键词，往往描述的是 Agent 的操作，而不是 Bug 本身。

| Bug 描述常包含 | 流程经验常包含 |
| --- | --- |
| 日志格式、模块名、输出行为 | source_refs、Read、Grep、revise_contract |
| 某个输入触发的异常 | 读取范围、证据引用、发布前提 |
| 一个框架 API 的表现 | 调用顺序、错误恢复、候选提交方式 |

5227 的历史讨论就暴露了这种错位：Issue 讲日志格式，卡片却讲引用范围。若只按同样的词是否出现打分，一张相关流程卡仍可能零分。

这不是按 Issue ID 实现了隔离，而是检索语义与经验表达没有对齐。

### 写入时需要给检索留下什么

经验不能只有“发生了什么”，还应说明“在什么情境下值得读取”。当前 name 和 description 就承担简短目录入口的作用；summary/detail 再解释原因、做法与例外。

例如，下面是说明机制的目录文案，不代表库里已经存在这张特定卡：

```text
name：修订契约前先展示完整引用范围

description：准备引用仓库源码修订契约，或收到引用范围未展示的拒绝时，
可查看这条经验，核对已读取的行范围。
```

它比仅写 `tags: source_refs, revise_contract` 更容易让模型联系到当前动作。标签依然有用，但不再是卡片是否能出现在目录中的唯一硬门槛。

### 当前检索如何适配

程序提供三个分类入口和数量，模型选择目录，阅读简短索引，再按 ID 取正文。目录没有关键词硬过滤；即使 Issue 没出现工具名，流程卡仍可被发现。

代价是模型需要作出目录选择，而且描述质量会影响选择效果。目录可达解决了“被零分过滤”的问题，不自动解决“模型一定选对”的问题。

当前遇到错误不会自动推送相关正文。模型可在已知目录入口上继续翻页、换类和读取，是否在运行中主动利用这些入口仍需要观察。

依据：[当前读取流程](../experience.md)、[目录视图实现](../../src/reproagent/experience_catalog.py)。

## P06：工具触发了，仍可能没有经验可以匹配

### 当时看到的表面矛盾

历史运行里已经出现 protocol_error、权限拒绝或保留发布步骤等触发记录，但检索仍返回 no_match。另一张卡讲的又可能是候选需要 grounded contract，与当次触发不是同一种情境。

早期方案还会依据分类和卡片引用的事实生成可用触发条件。如果卡片没有引用相关拒绝证据，或者条件生成/消费范围不一致，就会出现“系统确实撞坑，但卡片没有对应条件”的情况。

### 需要拆开的五个环节

```text
程序产生实际错误
  → 保留错误对应的受控事实
  → 学习卡引用这些事实并得到可用条件
  → 运行情境命中条件且内容送达
  → 模型采用建议，影响后续行为
```

第一步发生，不能证明后四步已经发生。单独统计触发事件数量，会高估经验系统实际发挥作用的程度。

### 一个受控码的例子

当前候选服务存在 `GROUNDED_CONTRACT_REQUIRED`，Controller 也有 `REVIEW_CONTEXT_TOO_LARGE`。这样的 code 应由程序在明确失败分支产生，而不是让模型从任意报错字符串猜测。

如果以后重新使用自动触发召回，需要同时检查：哪个组件产生 code；学习材料是否保存该事实；写卡时是否能引用；检索端是否识别；内容是否真的进入模型。只在白名单里多加一个字符串，不一定能打通整个链条。

### 当前方案保留了什么，改变了什么

真实受控触发事实仍可记录，卡片触发条件仍可作为来源元数据保留。但当前主要读取路径是分类目录和按需正文，事件发生不会自动召回或注入卡片，也不会决定某张卡能否在目录中显示。

因此这一问题主要沉淀为两条经验：不能伪造错误条件提高命中率；不能把事件发生、内容交付和最终收益计成同一个成功指标。

依据：[历史拒绝触发验收](../archive/reviews/2026-10-12-experience-rejection-triggers-acceptance.md)、[候选受控错误](../../src/reproagent/core/candidate_service.py)、[当前经验流程](../experience.md)。

## P07：自愿浏览在小预算下没有发生

### 为什么仅加一句提醒不够

用户回传的历史实验中，提示分别放在数据区和系统指令区，合计 0/9 主动查阅经验。模型已经知道有历史卡片，却仍优先继续改契约，没有花一个动作打开目录。

这说明“提供了工具”和“模型会把工具当作当前优先事项”是两件事。它只支持当时模型、提示、样本和配置下的判断，不能推成所有模型都不会自主查阅。

### 当前改成什么

当经验启用且存在非空可用库时，探索前先要求完成一次显式分类的目录浏览：

```text
提供 framework/model/workflow 的用途和数量
  → 模型选择一个分类
  → list_experiences(category)
  → 完整目录结果进入后续模型请求
  → 首次门禁解除
  → 模型自主决定读正文、翻页、换类或直接探索
```

必做的是一次目录发现，不是读取所有卡片，也不是每轮探索都先读经验。模型选中的分类为空仍可完成这次入口浏览；它之后仍可访问其他分类。

### 为什么不能只在提示词里要求

如果模型第一次直接调用源码读取或候选发布，程序在门禁未满足时不会执行该工具，而是返回明确的浏览入口。模型普通文本说“已经看过”也不能解除门禁。

门禁状态是任务级的 pending/satisfied/bypassed；契约修订或新阶段不会反复重新要求第一次浏览。这避免一次辅助要求扩散成整套持续探索限制。

### 为什么还有 bypass

如果模型连续两次不遵守，继续拒绝可能把任务全部耗在目录入口。所以第二次拒绝后记录 bypassed/noncompliant，并允许后续探索继续；这两次被拒绝的业务工具本身没有执行。

没有可用库、经验关闭、读取不可用或明确容量问题也有受控旁路。bypassed 是“未完成要求而放行”，不能计作目录已经交付。

### 已经证明和仍未证明的事情

离线验收检查了真实 SDK 下的首次分类、禁止提前业务副作用、空分类、后页读取、跨阶段状态和故障旁路。它证明门禁机制及消息交付成立。

它不保证模型随后读取正文，更不保证采用建议；这些需要单独记录。目录工具本身不调用模型，但选择工具的轮次与送入模型的目录文字仍使用已有动作和 token。

依据：[首次浏览实现](../../src/reproagent/adapters/agentscope/experience_browse.py)、[首次浏览验收](../archive/reviews/2026-10-13-experience-first-browse-acceptance.md)、[当前读取规则](../experience.md)。

## P08：索引太长吃上下文，只给前 3–5 条又可能漏掉所需经验

### 最初的几个矛盾

每个坑一个文件直观，但经验增多后会产生大量小文件；完全没有索引，则模型不知道有什么值得读。把所有经验一次性塞入输入虽然容易实现，却让无关正文长期占据上下文。固定只给前几条又会使后面的经验永远不可达。

因此需要把“怎么存”“怎么发现”“怎么加载正文”分开设计。

### 当前存储结构

```text
experiences/
  framework/
    experiences.json
    index.json
  model/
    experiences.json
    index.json
  workflow/
    experiences.json
    index.json
experiences.lock
```

每个分类的 experiences.json 合并保存多条卡，不为每个坑创建一个文件。三个分类分别容纳框架/环境条件、模型生成错误、探索与操作教训。

index.json 由程序从正文派生，是可丢弃缓存。模型负责提出卡片中的 name/description 等内容，不再独立维护第二份索引文件。

### 四层渐进式加载

| 层级 | 模型看到什么 | 目的 |
| --- | --- | --- |
| 分类入口 | 三类用途与冻结数量 | 判断去哪个范围找 |
| 一页索引 | 每条 id/name/description | 根据适用场景筛选值得读的卡 |
| 翻页或换分类 | next_cursor 后续页或另一个分类 | 扩大查找范围，不被固定前几条限制 |
| 具体正文 | name/description/summary/detail | 获取完整建议与边界 |

这里的“全部可达”不等于允许一次任务无限读取。当前每页最多 24 条，完整页面最多 8192 B；任务成功浏览最多 12 页、目录累计最多 16384 B；正文最多成功读取两次，单次响应最多 8192 B。所有限制共同生效，实际返回条数可能少于 24。

这些是当前版本的配额，不是经验分类的永久定义。达到限制后应明确说明没看完，不能让模型误以为其余经验不存在。

### 一个具体的查找过程

假设 workflow 分类有 40 条卡，第一页面内没有与当前操作相关的条目。模型可以沿 next_cursor 看后页，而不是只在前 3–5 条里勉强选一个；也可以认为应找 framework，转去另一个分类。

实际成功展示过的 ID 才能调用 read_experience。模型不能猜一个未展示 ID 直接读取；另一方面，正文没读到也不能被统计成采用了那条卡的详细建议。

### 索引和正文如何保持一致

当前任务使用启动时冻结的库视图，翻页不应混入中途新增卡片。程序通过来源指纹检查派生索引；索引缺失、损坏或过期时可以从正文重建。只读任务在内存恢复，不为修缓存写库。

正文写入和去重受锁与原子替换保护；若正文已经写成但缓存更新失败，应保留正文成功事实，下次仍能从正文恢复。正文损坏则不能靠覆盖或伪造空库悄悄“修好”。

旧单文件库仍有兼容读取和显式迁移路径。需要注意，卡片引用的原任务证据并不会随库迁移一起复制；删掉原任务后，可读建议与可重新审计来源是两件事。

依据：[存储与迁移说明](../experience.md)、[目录实现](../../src/reproagent/experience_catalog.py)、[存储实现](../../src/reproagent/experience_storage.py)、[分类目录验收](../archive/reviews/2026-10-12-experience-catalog-acceptance.md)。

## P09：工具调用成功，不代表内容已经交给模型

### 原来容易提前认定成功的位置

目录函数生成了结果，或者工具执行完成时，就把首次浏览状态改成 satisfied，看起来符合“已经调用过”。但中间还存在响应容量、格式化、权限处理和消息装配等环节。

如果目录没有完整进入下一轮输入，模型事实上没有获得那份索引。此时程序却允许它继续探索，首次浏览要求就只停留在工具日志上。

### 需要检查完整交付链

```text
目录函数得到一页内容
  → 形成最终工具响应
  → 响应成为 SDK 消息历史中的工具结果
  → 下一轮模型请求被格式化
  → 请求体中存在这次调用对应的完整内容
  → 才确认这次目录交付
```

这些节点之间可能出现失败，所以不能仅靠“函数被调用一次”或“工具返回 ready”认定最后一步成立。

### 当前门禁如何确认

门禁先暂存待交付目录的调用 ID、工具名、成功状态和完整 payload。后续输入中匹配到对应完整结果后才满足，不只检查一句类似的文本。

这能区分正常交付与以下情况：返回内容缺失；仅有摘录；关联了另一个调用；状态不成功；模型自行声称已经读过。发生容量或其他受控旁路时，也要记作 bypassed，而不是伪装 satisfied。

### 为什么使用真实 SDK 加 MockTransport

只 mock 目录工具返回值，最多证明函数能产生字符串。当前离线验收让真实 AgentScope 完成消息与工具装配，由 MockTransport 捕获实际序列化的 HTTP 请求，检查请求里调用关系和目录内容是否存在。

这能检验“下一个实际请求包含内容”，而不是只检验某个内部变量赋了值。因为响应由本地 transport 模拟，它不证明真实 provider 一定接受同样请求，也不说明模型已经理解或采用经验。

### 最终应如何解释结果

| 看到的事实 | 可以认定 | 仍不能认定 |
| --- | --- | --- |
| 目录工具被调用 | 有过浏览尝试 | 目录已完整交付 |
| 下一请求包含完整目录 | 目录交付成功 | 正文已读取 |
| 下一请求包含某卡正文 | 正文已送达 | 建议已采用 |
| 后续动作与建议一致 | 有采用迹象 | 一定由该卡导致，或一定改善结果 |

历史经验仍然是建议，不能因为已经交付就升级为本次原版源码引用，也不能改变本次需要满足的验收标准。

依据：[首次浏览交付验收](../archive/reviews/2026-10-13-experience-first-browse-acceptance.md)、[门禁状态实现](../../src/reproagent/adapters/agentscope/experience_browse.py)、[AgentScope 运行时](../../src/reproagent/adapters/agentscope/runtime.py)。

## P10：达到预算阈值后，应收窄探索，还是立即停止

### 最初的概念误区

讨论“达到步骤、时间、费用和风险阈值后，Loop 按设计收敛”时，最初把阈值理解成了硬上限，回答偏向直接停止。用户指出：阈值可以提前发生，此时还有剩余预算，期望 Agent 聚焦已有方向推进，而不是马上失去探索机会。

因此需要分开两件事：**软阈值改变接下来的探索策略，硬上限决定能否继续发起调用**。进入收敛不等于成功，也不意味着必须交出一个候选；证据不足仍应如实报告。

### 当前已有的控制与实际空档

当前步骤 guard 在每次逻辑模型调用前检查任务 Budget 并扣一步；取消、时间到限或步骤用尽有终止路径。HTTP 重试发生在同一次逻辑调用内，不额外增加探索步骤。

另外，已有“最后 3 步保留给阶段结束”的读工具拒绝机制。它防止模型持续读取直到耗尽，但属于尾部强制护栏，并不能代替提前提醒。模型可能在看到这次拒绝之前一直宽泛搜索。

阶段起点的 UserMsg 虽然含剩余预算，但一次 ReAct 探索阶段里可以连续调用多次模型。如果只在 Controller 切换阶段时更新，模型看到的数字就会过时。这也是为什么提醒必须进入每次实际模型输入，而不是只写在日志或阶段起点。

### 本轮选定的最小方案：先做步骤预算

以下步骤软收敛已实现并合并到本地 main，合并后再次通过 175 项定向回归；尚未 push，也未做真实模型效果对照：

| 时机 | 提供给模型的内容 | 程序控制 |
| --- | --- | --- |
| 正常探索 | 简短、实时的步骤事实 | 沿用当前工具与候选约束 |
| 达到步骤软阈值 | 剩余预算与聚焦当前路径的指导 | 允许剩余探索，现有权限仍有效 |
| 达到硬上限 | 不再发起新的探索请求 | 现有终止与有限清理/导出路径 |

第一版阈值取 `(3 × 总步数) // 4`。默认 20 步时，完成第 15 次调用及其工具处理后，**第 16 次请求**携带 used=15、remaining=5 和收敛指导；第 20 次仍可完成，第 21 次不能发出。这里的 remaining 包括准备发送的本轮。

提示在 AgentScope middleware.on_model_call 内、guard 扣步前构造，每轮临时追加并刷新，不永久堆入聊天历史。不为了提醒再调一次模型，也不让 Verifier 或学习调用继承这份探索策略。短提示会增加正常请求中的少量输入 token。

### 收敛时具体做什么

例如已经定位目标源码但还缺一段完整引用，且仍处于允许读取的范围，应定向补读这段，而不是重新遍历整个仓库。若拒绝原因没变，应处理缺失条件，避免只改措辞再次提交。

契约与依据足够时可发布最小候选；依据不够时，应按已展示事实修订，或者 request_information。真正执行、独立重跑与接受结论仍由 Controller 和验收路径控制。预算压力不能成为绕过来源证明、放宽断言或制造红色测试的理由。

第一版保留现有最后 3 步读工具拒绝。因此“必要时补读”也受现有权限约束；这版不会解决保留区内必要读取被拒的问题。是否允许有限补读需要另行评估，不能直接删掉曾经防止读到耗尽的机制。

### 哪些事情不能说已经解决

此次只覆盖步骤。当前 AgentScope 路径不支持配置硬费用上限，也没有统一风险阈值引擎；不能因此宣称时间、费用、风险软收敛均已实现。

即使日志记录了 converging，也只能说明程序作出了该判断。需要用真实 SDK 加 MockTransport 捕获下一次 wire_request，证明模型实际输入里存在新预算和指导。进一步证明模型减少了重复读取、提高了有效候选产出，则需要多次真实对照，不能用提示存在或单次 DONE 代替。

本次离线验收覆盖第 15/16/20/21 轮边界、同阶段刷新、跨阶段不归零、网络重试不多扣步、经验门禁共存、观测故障与历史不膨胀，集中回归 175 项通过。生成了离线 trace；浏览器 file: 安全策略阻止了点击验收，页面视觉/交互未验收。不能把这些结果写成模型实际更高效或四种资源阈值均已实现。

依据：[软收敛设计](../archive/specs/2026-10-14-exploration-budget-convergence-design.md)、[实现计划](../archive/plans/2026-10-14-exploration-budget-convergence.md)、[本次验收](../archive/reviews/2026-10-14-exploration-budget-convergence-acceptance.md)、[现有步骤预算](../../src/reproagent/core/budget.py)、[探索 middleware](../../src/reproagent/adapters/agentscope/middleware.py)、[阶段输入](../../src/reproagent/adapters/agentscope/runtime.py)。

## P11：验收失败不能只给结论，还要说明原因和下一步

### 这次讨论的问题

讨论从“模型只能提出完成申请，Harness 才能提交完成状态”开始。用户进一步问：验收失败到底由谁决定，失败原因又由谁判断？

这里有两个相互关联的挑战。第一，要防止模型把“测试变红”或“我认为已经复现”直接变成任务完成。第二，即使程序正确拒绝了候选，如果只返回“候选无效”“语义检查未通过”这样的结论，探索模型也可能不知道该改哪里，继续反复换假设、写测试，最终耗尽预算。

P01 已说明探索决策与任务状态的控制权。本条进一步记录验收内部的分工，以及失败结果如何成为下一轮可用的 Observation。

### 谁决定验收失败，谁解释失败原因

Verifier 是验收组件，其中既有程序检查，也有独立上下文的模型审阅；它不是一个只靠模型投票的 Agent。

| 角色 | 决定什么 | 结论边界 |
| --- | --- | --- |
| Verifier 中的程序检查 | 执行绑定、源码保护、进程清理、完整退出、探针、框架有效性、容量和引用等是否满足条件 | 可以确定对应检查是否满足；不能仅凭测试变红确定 Bug 语义正确 |
| Verifier 调用的审阅模型 | 断言是否有来源依据、是否触发目标行为、失败是否对应 Issue | 提供语义判断、理由和引用；判断仍可能错误或不确定 |
| Verifier 中的程序校验 | 模型回答格式是否合法、引用是否可用、成功声明是否满足要求 | 能约束和拒绝无效声明，但不能据此保证模型语义判断绝对正确 |
| Controller | 根据 Verdict 和实际预算/状态，决定继续探索、独立重跑、请求信息或停止，并在完成条件满足后提交 DONE | 模型的修复建议不能覆盖程序门禁、预算和终止条件 |

例如，命令超时由实际运行结果决定。程序可以返回 COMMAND_TIMEOUT，表示没有完整执行证据，不需要额外调用模型猜原因。只有程序前置条件满足，才进入独立语义审阅，判断失败是否属于本次 Issue。

“独立上下文”意味着审阅请求只看程序整理的契约、候选和执行证据，不继承探索聊天；不要求一定使用另一种模型。历史踩坑建议也不能作为这次原版验收证据。

### 现有完成门禁已经做了什么

模型发布候选后，Controller 验证发布记录，安排实际执行和验收。第一次被认可只能支持 SINGLE_OBSERVATION；同一候选再次运行、再次验收，并由程序确认失败一致后，才能支持 REPEATED_OBSERVATION。提供兼容修复版且相同候选通过时，才能进一步支持 DIFFERENTIAL_VALIDATED。

成功导出后由 Controller 提交 DONE；没有通过验收的模型文本不能直接提交该状态。DONE 不等于差分验证通过，证据等级与修复版状态仍应分开解释。

因此，此次问题不是“缺少完成门禁”，而是“已有门禁拒绝后，部分反馈不够具体”。也不要求每条任务机械叠加五种验证：当前任务采用结构、环境、确定性检查和独立语义审阅，没有强制人工签署。

### 为什么一句拒绝理由不够

不同失败需要不同处理。候选语法错误应该改测试；预期行为缺少来源应该查原版依据；执行超时需要检查执行障碍或缩小候选；语义判断不确定则需要检查证据，不能直接当作已经证明 Bug 不存在。

现有 Verdict 已有 reason、evidence_refs、unmet_checks、next_action、候选/契约/run 绑定和 execution_diagnostic。执行类诊断已经能保留具体事实，连续命令超时和证据超限去重也已有程序处理。

修复前，部分其他失败分支主要返回自由文本，未提供结构化检查缺口。next_action 只有少数值被 Controller 特殊处理，不能把现状描述成已经实现通用的修复、重新规划和转交调度器。

实施前，候选验收反馈经 Controller.feedback 按 8192 UTF-8 字节直接切片。即使完整 Verdict 保存得正确，送给下一轮的文本仍可能被截断，损失关键原因、建议或 JSON 完整性。这是记录存在与模型实际获得信息之间的又一个差距，与 P09 的交付问题相关。

### 本轮提出的修复设计：一张具体的返工通知

以下是设计中的说明示例，不是本轮新跑的真实案例：

```text
问题：尚未确认目标行为被触发。
依据：审阅模型根据本次已提供的候选与运行证据，未确认目标触发。
下一步：检查候选的实际调用路径及证据，必要时修改后重新提交。
边界：这是审阅判断，不是程序证明目标行为绝对没有执行。
```

方案沿用 Verdict，增加可选的结构化 issues，提供程序预定义的错误码、实际检查、结论来源、说明、有效引用、程序测量和恢复建议。程序事实标记 program_check，语义判断标记 provider_claim。未知原因保持未知，不能为每次拒绝强行编造根因。

模型不自由生成错误码：程序从已校验的回答和实际检查生成诊断。现有语义字段允许 false 表达不确定，因此映射为“未确认”比“已经证明不匹配”更准确。格式无效的回答也不能被包装成可信语义结论。

Controller 保留现有终止与接受优先级，依据受控字段组织下一步反馈，不通过英文理由关键词猜测策略。恢复建议只说明值得尝试的方向，不保证一定可修复，也不自动放宽权限或增加重试。

完整诊断仍保存到本次 Verdict；面向下一轮的反馈则使用有界投影，在 8 KiB 内优先保留主错误、失败检查、关联身份和建议。多余细节有序省略并明确标记，不直接截断 JSON。最小反馈或整个阶段输入仍装不下时，需要明确停止，而不是让模型在缺少关键材料的情况下继续。

### 如何证明修复有效

第一层检查每个实际拒绝分支是否产生有依据的结构化缺口，未执行的检查是否保持未执行，模型不确定性是否被保留。原版保护、来源、重复一致性和完成门禁仍需保持原拒绝效果。

第二层验证旧记录兼容、新记录往返、中文多字节和大量引用的容量边界，并确认完整 Verdict 不会因反馈缩减而被改写。现有单次超时后继续、连续超时停止、证据超限去重和取消/清理优先级应继续生效。

第三层使用真实 AgentScope SDK 加离线 MockTransport 捕获下一轮序列化请求，检查主错误、失败检查、建议和省略标记确实到达模型。仅在 trace 或内部字段看到它们不算完成交付验证。

这些离线验证只证明机制和送达。是否减少盲目重试、提高真实 Bug 的复现率，仍需真实案例的重复对照，不能用一份设计或单次成功宣称解决。
